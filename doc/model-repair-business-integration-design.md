# 模型修复业务接入：实施与交接

更新：2026-10-18。按用户要求收敛为唯一修复流程，删除业务版本号和新旧切换开关；复核后与原功能合并入库，不推送或部署。最新范围与验证状态见[本轮验证与交接](../docs/ai/validation/2026-10-17-model-repair-staged-gui.md)。目标服务器与真实存储联调、业务阈值验收及 SDK 商用授权仍是发布条件。

## 1. 结论与范围

复用现有链路：**主服务 → PDS 独立模型任务 → 分阶段调用同一个 Orca 程序 → PDS 选定一个模型 → 主服务继续后续节点**。

不新增微服务、数据库表、消息队列、通用工作流引擎、MeshLib 独立程序或新修复算法。首版只处理无色单 STL，单位毫米；不接管普通切片中的 repairModel 开关，不改原生 GUI，不迁移管理端旧 StlRepairApi，不自动转换彩色 OBJ/复杂 3MF。

## 2. 为什么不是重新做一套

- PDS 的 `ModelRepairTaskProcessor` 只区分两种业务：CHECK 使用原有独立检查；修复统一调用 `ModelRepairWorkflow`。原 `--auto-repair-model 1 --export-stl` 的独立任务执行和结果解析分支已删除，不保留新旧双轨。
- `model_repair_job` 已有 request_json/result_json LONGTEXT，可保存策略快照、简要阶段结果和已选模型，不需要增加任务表。
- `ProcessBuilder(List)`、独立目录、输出 realpath 范围校验、进程树超时、并发控制均可复用。
- 主服务两个 handler 统一读取 PDS 最终模型，包含 failed 时已经保留的成果；不再按业务版本或旧 repairStatus/outputModelUrls 另选模型，不把兜底误记成修复成功。

### Orca 报告设计

新增可选 `--model-stage-report` 和 `--model-reference ORIGINAL.stl`，输出固定为本次输出目录的 `model-stage.json`，协议为 `orca_model_stage_v1`。不传参数时不增加几何比较成本、不改变现有输出。统一报告字段控制在以下范围：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 协议版本、阶段、输入 SHA256、比较基准 SHA256 |
| 产物 | 本次交付文件、SHA256、是否完成导出回读 |
| 检查 | passed / defects_detected / incomplete 的结构化状态、七类缺陷、实际检查完整性 |
| 变化 | 包围盒偏差、双向表面采样偏差、前后连通部件数及统计完整性 |
| 重建建议 | 复用已有 schema2 assessment / reason / applicability，绑定对应产物 SHA256 |
| 执行 | 正常完成或失败原因；不等同于模型无缺陷 |

报告在本次文件、复检、必要比较均完成后原子写出。**首版不做 Orca 进程内部的中途恢复协议：本次调用失败、超时或报告不完整，就不采用本次新文件，业务沿用上一完整阶段。** 即使目录里残留 result.stl/candidate.stl 也不能捡来使用。这样不需要从 Orca 某个失败子步骤中抢救尚未被业务接受的成果。

新报告模式直接检查实际导出 STL 的原始坐标，检查、截面依据、文件身份保持一致；不拿 Model 导入居中后有浮点差异的视图代替交付网格。原子发布不覆盖已有报告，且不能替代进程退出码检查：消费者必须同时验收退出码 0、报告及产物 SHA256。

高级阶段的“部分修复”仍可正常交付，不能按重建的零缺陷标准全部拒绝。检查资源不足/未知执行错误与已知缺陷导致的结构判断受限必须区分，不能只看一个 check_complete=false 决定是否高级修复。

## 4. 分阶段规则

一个任务只维护原始文件、当前已选文件和本次候选。每阶段最多一次，不自动换算法、调粗精度或反复重试。

| 顺序 | 调用 / 判断 | 结果 |
| --- | --- | --- |
| 0 | 提交任务时固定实际修复参数和时限，把受控不可变原件引用作为初始已选模型写入 result_json；然后才 dispatch 入队 | 排队拒绝、尚未执行就重启也有兜底；下载后在 PDS 内部计算文件身份，不向主服务重复传递顶层哈希 |
| 1 | Orca `--check-model`；注意该入口会执行既有基础导入整理 | 完整健康则结束；明确残留缺陷才进入高级；资源/执行异常不升级。整理后的文件也必须通过对应变化选择，不能把检查整理偷偷当作完全无改动 |
| 2 | 同一原件快照调用 `--check-model --repair-model cgal --repair-evidence` | 高级阶段重新走同一导入基准，不把第一次 prepared 再反复导入整理。通过本阶段交付与变化规则后才保留结果；完全修好则结束，正常未解决才判断重建 |
| 3 | 检查当前保留文件对应的 assessment=evidence_present 且 applicability=eligible | 才调用 `--reconstruct-model --reconstruction-engine meshlib`，传明确体素与资源参数。undetermined/blocked 不自动升级 |
| 4 | 重建完成、完整独立网格检查及导出回读通过、文件身份匹配，再检查变化阈值 | 全部满足才提升已选模型；否则保留高级/基础/原始中最后已接受的一份 |
| 5 | 返回一个选定模型及来源、检查结论、采用/拒绝/异常原因 | 下游使用该文件；不在本节点切片、生成打印路线或宣称可打印 |

证据只用于它所绑定的文件。高级成果因变化超限被拒时，首版直接保留之前模型并结束，不能拿被拒模型的建议去重建另一个模型。高级正常无进展时，只有它的证据对应文件与实际保留基准一致，才可继续重建。任何未知/缺失版本、hash 不匹配或统计不完整，均不自动采用。

检查阶段的 prepared 因变化规则未被采用时，首版同样停止升级并返回原件，不能把 prepared 的 passed 结论写到原件上。最终检查结论与最终文件身份绑定；原件没有对应的检查证据时，mesh_status=unknown、repairPassed=null，阶段报告仍保留实际查到的问题。

三类重建依据继续由 Orca 判断：高级后仍有已证明的真实穿透；完整参考截面都无法构造有效区域；残留开边且调用方明确允许补封。第三类默认关闭，不从 STL 后缀推断允许封口，也不复制成后端缺陷计数规则。

## 5. 自动选择：一个保守策略，不做评分系统

高级/重建的变化都与**同一个原始输入快照**比较，而不是只与上一版比较，避免多次小改累计成大改。比较基准通过只读、无再次修复的方式加载；拓扑统计口径必须一致。复用现有有界采样比较，不新增 Java 网格算法。

采用规则：

1. 本次调用正常完成，业务报告版本/输入/产物身份匹配，导出回读通过。
2. 高级成果满足现有引擎接受规则，可为部分修复；重建成果必须完整通过网格检查。
3. 包围盒偏差和两个方向的表面采样偏差均不超过配置的毫米阈值；缺失、NaN、无有效样本或比较未完成不能当作 0。
4. 首版连通部件数量必须不变，且统计完整；变化时不自动采用。它不是设计零件数量或部件一一对应证明，而是保守拦截条件。

只保留三个业务参数：允许偏差 mm、MeshLib 体素 mm、允许补封开边（默认 false）。任务提交时保存实际参数快照，运行中不随配置热更新漂移。

审核用建议起点：允许偏差 0.25 mm，体素 0.0803 mm。前者借用现有偏差告警量级作为**待验证的业务候选阈值**，后者仅已有 Q 样本回归依据，均不是通用精度保证。生产启用前必须用实际业务样本验证并固化；不能仅因数值已写进配置就称通过商用验收。

此保守策略会拒绝一部分有帮助的重建：历史 Q 结果存在 source→candidate 采样约 4.46 mm、连通壳 16→10，将不被自动采用，最终仍可交付之前的模型。这是明确的安全取舍，不应为了让 Q 自动通过而临时放宽全局规则。采样通过、部件数不变也不证明孔洞、关节间隙或薄壁完全保真；结果继续保留结构未确认状态。

## 6. 文件与失败：沿用现有存储，保留一个已选引用

- 新流程仅接收有权限的受控 OBS/CDN 对象，不开放任意 URL 下载；域名复用现有 `ModelFileService` 定义，不另设修复专属域名配置。下载实际字节上限 256 MiB，并受总时限限制。主服务鉴权，PDS 入口仅受信内部调用；不能把字符串域名检查当成对象归属授权。
- 原件必须有稳定存储引用；首版要求主服务已保存原件，临时或可变链接须在提交入队前转为不可变快照。原件引用与任务同时入库，不能等 Processor 开始执行才记录。文件内容无法取得或存储整体不可用时，返回真实失败及已有原件引用，不能伪造新文件交付成功。
- 已通过选择的阶段文件上传到 `model-repair/<jobId>/<stage>/<sha256>.stl`，不覆盖旧对象。原件已有可靠不可变引用时可复用，不重复上传。
- **上传成功 → 条件更新任务 result_json 中的已选引用 → 继续下一阶段**。新版本上传失败则不提升，沿用上一持久版本。
- 报告文件路径限制在当前阶段真实目录内，校验 SHA256，不根据 glob、文件名排序或退出码 0 猜测正确产物。
- 正常完成、排队失败、进程异常、整体超时、重启恢复均走保留当前已选引用的终结逻辑。保留现有 processing/success/failed；失败也能带最终模型，但不改成修复成功。
- 保留原有 status=processing 条件更新；选择提升与超时终结通过短数据库事务/行级锁或等价原子更新排序，终态后不得覆盖模型。上传不放进数据库锁内，超时已终结时放弃晚到结果。
- 修复任务重启后不做复杂断点续算或自动重放：周期扫描只恢复原任务总截止时间监控，到期以数据库最后保存模型终结。不能仅因没有执行锁就提前终结，它也可能是其他实例刚入队、尚未执行的正常任务。独立 CHECK 保留原有锁检查及重排规则；这是业务区别，不是新旧修复版本，不新增 owner/心跳协议。
- 复用当前任务 600 秒总期限、进程 300 秒上限与并发控制，单阶段用剩余预算而非重置总时钟；主服务当前 900 秒外层等待保留余量。超时必须停止并回收进程再释放执行资源；不把 Future.cancel 等同进程已退出。
- 生产部署须保证 Java 服务退出时，其 Orca 子进程也被回收（例如受控容器/系统服务进程组，Windows 对应 Job 机制）。恢复流程不能只看 Redis 锁消失就假定旧子进程已退出；未配置和验证这一点的平台不宣称完成故障回收验收。
- 首版不增加跨服务取消 API，主服务用户取消后仍由 PDS 总期限约束远端，晚到结果不得恢复已取消主流程。若产品要求立即取消远端，再单独扩展。
- 所有本地副本在引用持久化后清理；只保存简短阶段摘要与必要诊断，不把巨量网格明细塞进 result_json。服务器容器/系统内存配额继续约束整个 Orca 进程，SDK 协作 RSS 不是硬上限。

## 7. 接口兼容与实施顺序

- 现有公开请求保持只有原来的模型地址，不增加客户端 workflow 参数。独立修复任务统一执行一个流程；删除 `workflowVersion` 和 `staged-workflow-enabled`，不保留业务版本分流。实际参数和时限写入 request_json；独立 modelCheck 接口不改变。
- 结果包含明确的最终模型 URL、来源阶段、选择原因、实际参数和简短阶段状态；outputModelUrls 保留且只有一个最终 URL。顶层重复哈希字段已删除，实际文件哈希验证仍在 PDS/Orca 完成。阶段四种来源由共享 `ModelRepairStage` 常量定义。
- 主服务收到终态后读取明确最终模型，包含 failed 时的有效兜底；不再自行取多个候选中的第一个。repairPassed 仍表示所选模型的实际检查结论：兜底或未解决不标为修复通过；任务正常结束可以为 success，执行异常保留 failed，两者均返回已选模型。业务节点可以正常继续而修复记录保留失败。
- 主服务沿用已有结果 JSON，不加模型表列。缺关键字段或模型地址无效时退原件，不保留旧修复协议解析分支；已完成的任务沿用已保存交付地址，不重新修复。
- 发布前排空旧进行中任务，配套升级 PDS interface、PDS 和主服务，Orca 必须已具备阶段报告与 MeshLib 能力。不支持新旧混部，不增加迁移框架；回退需整套回退部署，不再提供流程切换开关。
- 主服务保留已有 `success/not_required/fallback/fallback_pass` 等 outcome 值，不新增客户端枚举。兜底不是检查通过，也不会将已保存的高级成果误换回原件。Orca 报告 schema 仍校验，它是文件格式约束，不是业务版本分支。

## 8. 商用上线前的验收门槛

本方案是面向上线的最小范围，不是当前已可发布的承诺。

1. 真实 CLI + 后端契约回归：健康、基础整理变化、高级全修/部分/无进展、三种依据、重建通过/失败、阈值边界、部件变化、指标缺失、报告/hash 错配；验证统一原始基准。
2. 故障回归：排队拒绝、超时/强杀/缺库、导出/回读/比较/上传失败、DB 竞争、重启恢复、晚到写入；均不采用残留新文件、不覆盖原件，并交付最后可取得的持久版本。
3. 主服务两个消费入口回归：失败但保留高级成果不丢失；兜底不显示修复成功；普通切片、OBJ 绕过与旧接口不受影响。
4. 目标服务器原生验收：Linux/Windows 的 SDK 依赖、ABI、无桌面运行、普通切片与 MeshLib 共存、并发峰值和 OS 资源约束。已有 Mac 测试不能替代这些验证。
5. 用户此前明确 SDK 商用及再分发授权尚未取得；发布前完成适用授权确认。此设计不构成已经有权商用的证明。
