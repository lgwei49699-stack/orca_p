## 测量方法

- 旧 Mac 程序对应 `d512c9b4ec`，与 2.3.2 标签 `manual-build-linux-20261103-03` 的重建源码一致。新程序为同基准上的本地改动。二进制 SHA-256 前缀分别为 `eaa6ad2d2645`、`518feaeb7141`。两版使用相同 SHA-256 的 MRMesh 和 MRVoxels 运行库。
- 两版直接对同一原件显式重建。0.30 mm 为主对照，dragon 增测 0.128 mm，每次给引擎 180 秒、2048 MiB 协作预算、100 万输出三角面。两版按模型交替先后、串行运行。每件每档每版计一次，另对回归样本抽查复现。原件执行前后均核验 SHA-256。
- 墙钟包括程序启动、原件导入、重建、候选验收及成功时的 STL 导出。峰值 RSS 来自 macOS `/usr/bin/time -l`，另在原始 JSON 留存引擎按 physical footprint 观测的内存；2048 MiB 约束后者，RSS 可以高于该值。
- 通过要求正式 CLI 返回成功，输出 STL 存在，mesh_validated 为真且七类网格检查均完成、计数为零。直接重建得到的比例只用于版本对照，实际 App 会先分流。CLI 结果未做实物打印。

## 2026-11-06 CLI 资源控制最小改动方案

按用户要求，采用固定请求精度、启动前格数筛选、现有资源保护。阈值配置待定，本节为待实现设计。

### 改动范围

1. ModelStageReport.cpp 在现有 geometry 中补充 size_mm 三轴尺寸数组，来自已经计算的修后 candidate_bounds。既有字段保留，报告继续关联实际阶段产物。
2. ModelRepairWorkflow 在高级修复结果可接受且有重建依据后、创建重建进程前，以当前实际选定体素和 size_mm 计算包围盒格数。格数预算超出时保存现有 skipped 原因，保留阶段产物及残留缺陷，结果为 unresolved。只增加一个直接判断/小函数。
3. 使用 ModelRepairConfig 及现有 policy 保存格数上限、重建阶段时限，最多增加两个服务配置项。精度沿用请求值。重建阶段预算取专属时限、通用进程时限及任务剩余时间的最小值，调用既有 execute 和进程回收。
4. Orca 已有的内存预估继续在 SDK 启动前执行，服务透传现有内存参数；引擎协作停止和服务进程截止继续负责实际运行边界。

流程为：检查 → 按需高级修复 → 复查 → 按格数决定是否允许自动重建 → Orca 既有内存预估 → 单次重建 → 既有结果验收。

体素格数采用三轴尺寸和最终体素计算，包含约定的边界余量，有限数值和乘法溢出检查复用现有入口校验习惯。沿用现有数据兼容策略处理历史任务；旧阶段报告缺少 size_mm 时，明确记录本次未执行格数筛选，继续由已有引擎准入和运行时限保护，避免把缺失尺寸当零或使用最长边立方冒充包围盒。
