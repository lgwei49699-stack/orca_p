# 文档维护与提交检查

规范适用于两条分支；正文与指纹属于当前 Git 快照。模块索引见 [README](README.md)，机器范围见 [modules.json](modules.json)。旧 `doc/` 仍用于专题/Wiki；不移动到新的发布流程中。

## 范围与命名

- 模块以业务职责划分，ID 使用小写短横线，正文为 `docs/ai/modules/<id>.md`。无需为每个 C++ 文件建说明。
- 清单 `sources` 是唯一归属，`watch` 是共享实现依赖，`tests` 是相关验证源码；三者都进入该模块指纹。entrypoints 必须是快照里存在的实际文件，test_note 明确验证边界。
- `*` 不跨目录，`**` 跨目录；方括号按字面处理。单一职责目录递归覆盖内部文件，共享平铺目录按文件登记。新增第一方文件/目录未匹配必须报错；重复归属或一边归属一边排除为清单错误。
- 检查对象为 Git 跟踪文件及工作目录中未忽略的新文件。build、planning 等忽略产物不在范围内；主动新增源码不可放进忽略目录规避检查。排除项必须有理由，不能新增笼统 `src/**` 排除。
- 第三方快照、旧参考文档和历史运行产物的排除已登记；依赖集成脚本仍有模块归属。文档自身不参与源码指纹，避免循环依赖。清单／正文是否准确仍需要人工或 AI 读代码判断。

## 模块正文模板

每份正文包含：职责与边界、入口与调用、核心流程、配置与约束、失败与取消、修改与验证、关联模块。存在实际分支差异时补充分支现状；共用模块不重复历史 HEAD 或初始化流水。链接专题，不复制另一分支的测试结论。

```markdown
# 模块标题

<!-- module-review
{
  "id": "模块 ID",
  "source_fingerprint": "运行 --fingerprints 后人工核对并填写",
  "reason": "本次复核的具体差异、更新段落或无需正文修改的原因"
}
-->

## 职责与边界
说明输入、输出及不归本模块负责的工作。

## 入口与调用
链接实际文件，说明调用者、核心接口与下游。

## 核心流程
解释业务数据经过哪些阶段，以及何时提交结果。

## 配置与约束
解释生效值、覆盖/继承、单位和边界。

## 失败与取消
说明拒绝、回退、事务和取消检查的行为。

## 修改与验证
列常见改动位置、已有测试和未覆盖场景；测试存在不等于已通过。

## 关联模块
链接同分支相关正文和已有专题。
```

涉及 GUI／CLI 共享业务时，在“入口与调用／配置与约束”写两端入口、共享实现和生效配置，在“修改与验证”写自动化／CLI 检查及 GUI 验证记录链接；另一端不适用需说明具体理由。无需把整份手测流程复制到每个模块。

模板只供写作，不能复制空章节作为完成。脚本检查结构和身份，不能验证自然语言结论正确；reason 不是自动审核证明。

## 命令和快照语义

从仓库根目录运行；Python 3.9 及以上标准库与 Git 即可，不安装依赖。

```sh
python3 scripts/check_ai_module_docs.py --all
python3 scripts/check_ai_module_docs.py --staged
python3 scripts/check_ai_module_docs.py --base master
python3 scripts/check_ai_module_docs.py --all --fingerprints
python3 -B -m unittest discover -s scripts/tests -p test_check_ai_module_docs.py -v
```

- `--all`（默认）：当前工作目录，包括未忽略的新文件。所有模块检查覆盖、正文结构、入口、内部文件链接及指纹。
- `--staged`：暂存区源码、清单与文档组成的快照，相对 HEAD 选出受影响模块；未暂存的文档不能使该检查通过。覆盖与入口校验仍检查整份清单。未建立 HEAD 时检查整个暂存快照。
- `--base <ref>`：当前已提交 HEAD 相对指定 ref 的累计变化，不含暂存/未暂存内容，不自动取 merge-base。若要看分叉以来变更，显式传入 `git merge-base` 求出的提交 ID。审核分支时不要误把工作目录结果当提交内容。
- `--fingerprints`：与以上模式组合，只打印应记录的指纹，不修改文档、不宣称复核完成；默认针对全工作区。
- 指纹为排序后的归属/依赖/测试文件路径、Git mode、Git blob 内容 ID 的 SHA256。工作区用 Git hash-object 计算文件身份（不写对象），原始字节与暂存区一致的旧文件保留原 blob 身份，变化/新增内容按当前 Git 属性规范化；暂存/提交从对应 Git 树读取。路径变更、内容变更及删除会改变指纹；不含 mtime、文档日期或尚不存在的提交哈希。
- 退出码 0=通过，1=未归属/缺文档/失配等需复核，2=脚本/Git/清单错误。不调用编译、切片、CodeGraph、网络或正文生成器。

## 共享参数与复核成本

`PrintConfig.cpp`／`PrintConfig.hpp` 由 presets 归属；参数面板、分盘、FFF 切片、墙、填充、支撑、筏层、附着、多材料、G-code 导出及 SLA 通过 watch 记录依赖。公共默认值、单位或字段类型改动时，会提醒同时复核相应说明，避免只更新 presets 而遗留筏层等文档中的旧值。

此提醒按完整文件内容计算，不解析 C++ 语义：只改筏层参数时也可能提醒其他配置使用模块。逐项核对差异后，无关模块只需记录“本次只改哪些键，本模块依赖未变”的具体理由并更新指纹，不要求改写整篇正文或额外运行无关业务测试。新增参数使用方或跨模块调用时，修改清单 watch；源码覆盖完整不等于调用依赖已自动发现。

检查内部仅缓存本次快照的路径匹配、目录及已提交／暂存 blob 读取；不同快照不共享内容缓存。精确文件名直接查找，通配路径按既有规则匹配。仍计算 Git 内容身份，不用文件时间跳过审核，不生成审核正文。

## 每次入库前

1. 确认分支、差异和当前工作区已有改动；不覆盖其他人的文件。
2. 用清单定位受影响模块，读实际变化与调用上下文；列出 GUI／CLI 接入及配置覆盖，核查共享功能同步。业务、接口、配置、异常/取消和验证结论变化时更新相应段落。
3. 纯格式化等不改正文时，仍在 reason 写明具体复核原因，再填新的源码指纹。仅修改日期或机械批量填指纹不能算审核。
4. `--all` 通过后选择性暂存本次源码及对应文档；运行 `--staged`、`git diff --cached --check`，审阅暂存差异。若之后又暂存了代码，重新执行检查。
5. 合并/cherry-pick 时按目标分支重新复核；不要从另一分支只复制指纹。源码相同可以复用内容，仍需检查入口和分支边界。
6. 按 [验证规范](validation.md) 核对构建并完成相关自动化／CLI 检查；缺构建时由 AI 补齐必要目标。需要用户 GUI 手测时，先按 [交接规范](gui-validation.md) 写好具体步骤与 MD，再交给用户；不能只给一句“待 GUI 验证”。
7. 提交报告分别说明自动化、CLI、GUI 的结果、证据及待验证／不适用项；不得把两端尚未验证的业务宣称全部完成。提交时如仍有待 GUI 项，明确列出范围与风险；是否入库按用户当次要求处理，不将整体验收写成完成。聚焦/完整测试不叠加计数，不收 result.json、日志或本地索引。

本项目选择 **AI 提交前必查 + 开发者手动运行**。不安装 Git hooks，不新增强制 CI。脚本不会自动暂存或提交；仅有通过输出不能替代内容审查。

## 多轮任务的进行中记录

复杂任务在开始调查／编码时就确定一份进度 MD，由 AI 主动持续维护，不等完成、提交或上下文将满时才补记。优先复用该功能的专题／验证记录；没有记录时在 `docs/ai/validation/<日期>-<任务>.md` 建立，任务相关模块或索引提供入口。文档治理任务可直接使用 [文档验收记录](validation-report.md)，同一任务不另建多份重复台账。

### 记录内容与更新时间

- 文件顶部维护简短“当前执行状态”：目标与不改范围、分支／HEAD、未提交改动范围、当前步骤、最后已验证的源码／构建身份、未验证项及下一步。正文下方保留必要的步骤和决策历史，避免每次续接全文重读。
- 开始一个会改变基准的逻辑步骤前，记下步骤目标、拟改范围及验证办法；完成该步骤后立即记录实际改动、结果与后续动作。长构建／测试启动前记命令和日志路径、标为运行中，结束后回填退出码和统计。
- 用户修正范围或新增约束、定位到关键证据、采纳／否定方案、修改一批代码、构建／测试成功或失败后，及时更新记录再进入下一个依赖步骤。需要向用户交接或结束本轮前确认状态已落盘，不依赖用户提醒。
- 关键决定记录“结论、理由、适用范围、证据”；明确区分假设、已确认、已否定和待验证。失败尝试保留原因和停止条件，防止下一轮重新走已排除的方案；不要记录逐字聊天或内部思考过程。
- 基准包括当前 Git 状态及关键源码／配置／输入身份；未提交变更不能只写 HEAD。旧测试结论必须关联当时的代码和程序，新源码未验证时保留待验证；更换分支或发现外部改动后重新核对。
- 记录以一个可复核的逻辑步骤为单位，不要求每次 rg、每个工具调用或每行代码都写一条。只保存必要文件位置、决定、结果、命令与证据路径；原始日志另存。简单低风险单步任务不强制创建独立进度文件。

### 续接和完成

恢复任务时先读顶部当前状态和相关决策，核对分支、差异与最后验证身份，再继续下一步。状态与实际文件不符时先检查差异；文档记为运行中不代表进程仍在运行，核实进程／日志后处理，不能盲目重复启动。突然中断可能发生在记录更新前，因此记录是接续依据，不能替代当前源码。

功能完成后，把稳定业务结论归入模块正文，步骤及证据保留在同一专题中；更新当前状态为完成或明确列待 GUI／待验证事项。此机制由 AI 执行，文档检查器不理解过程语义，不能自动保证每项重要决定已记录；交付时给出实际更新的进度 MD 路径。

建议使用以下紧凑结构，按任务填写，不复制空模板充当记录：

```markdown
## 当前执行状态

目标／边界：
分支、HEAD、未提交改动及源码／配置身份：
当前步骤与已完成事项：
最后验证身份和结果／尚未验证：
下一步：

## 关键决策

| 决定／约束 | 理由及证据 | 状态／适用范围 |
| --- | --- | --- |

## 步骤记录

| 步骤／时间 | 目的与变更范围 | 实际结果／证据 | 状态与后续 |
| --- | --- | --- | --- |
```

## 上下文与长任务

- 仓库、分支和差异在新会话／切换分支时核对；同一任务内优先复用已确认的信息，文件变化或依据不足时再读。根规则已由客户端提供且版本一致时，不再用工具全文输出一遍。
- 从模块索引定位后只读相关正文和源码片段；不全量读取 35 份文档、modules.json、历史归档或长进度流水。长日志先按时间／关键词定位，必要时扩大上下文；原始结果留文件，工具返回摘要、失败片段、统计和证据路径，不能隐藏失败。
- 字符串搜索先缩小目录、文件与输出范围；工具发现只返回相关工具名，测试通过只记录必要统计。出现截断时改用定向读取，不反复输出同一大段。内容哈希／映射检查仍完整执行，缩短的是返回内容。
- 按[进行中记录](#多轮任务的进行中记录)在关键步骤后及时更新当前状态，不只在跨对话／交接时补记。恢复时按需读取当前状态及相关证据；历史失败不整段复制进摘要，同一任务不为每次回复新增文件。
- 上下文压缩后先用续接点和当前 Git 状态恢复；证据未变化时不重复已完成搜索／测试。记录替代重复阅读，不能替代当前源码或验证证据。
- 一个长任务可持续在同一对话完成；当用户转到独立业务或需要减少历史负担时，建议新对话只携带简短状态和文档路径。未经用户要求不自动创建／切换对话；不把全部旧消息、截图和日志粘进新对话。
- 不为减少压缩盲目扩大模型上下文或关闭压缩。AGENTS 精简不会自动清掉旧对话已携带的文本；上下文阈值属于客户端／模型设置，未经核实不改。这里只约束文档和读取行为，不承诺压缩次数或耗时。

## 持续优化边界

当前 35 个模块、共享规范和内容指纹足以作为迭代入口；不按文件数量继续拆文档。每轮重点补真实变化对应的调用关系、两端配置和验证证据。只有出现独立业务职责才拆模块；同一流程反复导致漏测时再补共享测试／工具，不为低影响文案或纯文档强制执行全量业务回归。

脚本只能检查归属、结构、链接和内容身份，不能证明正文正确或 GUI／CLI 行为一致。具体交接记录按需创建；当前事实留在模块，历史结论留在专题，原始日志留本地证据目录，避免根规则再次堆成长篇流水。
